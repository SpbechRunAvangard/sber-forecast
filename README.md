# Прогноз продаж по складам и товарам (SpbTechRun, команда «Авангард»)

Недельный прогноз продаж для 11 складов × 799 артикулов (8 789 рядов) на 9 недель вперёд и Docker-контейнер
с HTTP-API на FastAPI. В контейнере работает итоговая модель **v6** — та же, что дала основной submission:
на полных данных по 2026-07-26 контейнер выдаёт файл, совпадающий с `data/submission_weekly_v6.csv` байт в байт.

## Описание решения

1. **Данные** (`src/data.py`). Продажи суммируются по департаментам и городам до уровня дата × склад × артикул.
   Остатки (на начало дня) — сумма всех строк с одним ключом, отрицательные (резерв) сохраняются, дни без записи —
   пропуск. `sales_sum` и `discount_sum` хранятся как `np.log`: перед суммированием по дню применяется `np.exp`,
   как разрешает ТЗ; в признаки идут только отношения (цена сейчас к цене за полгода, доля скидки).
2. **Признаки** (`src/features.py`, ≈ 80): 22 базовых признака ряда (средние продажи за 7–180 дней, доля дней
   с продажами, остатки, склад, категория); недельные; прошлогодние (продажи тех же 9 недель год назад);
   артикул по всем складам (спрос, тренды, число складов с продажами, остатки); склад и категория × склад;
   цена и скидка; динамика остатков ряда.
3. **Уровень** (`src/model.py`): две модели LightGBM Tweedie (на 22 и на всех признаках) предсказывают средние
   недельные продажи за 9 недель; уровень = среднее × сезонная поправка^0,5 × 0,9, округление до целых.
   Сезонная поправка — продажи тех же 9 недель год назад к уровню 90 дней до них по всем рядам.
4. **Решение «0 или уровень»**: третья модель LightGBM оценивает выигрыш SMAPE от ненулевого прогноза; ряд получает
   уровень (не меньше 1), если выигрыш > 0 и уровень ≥ 0,5 шт./нед, иначе 0. Прогноз одинаковый на все 9 недель.

Проверка на четырёх 9-недельных периодах (включая сезонный 28.07–22.09.2025): ориентир score 0,785 против 0,807
у первой версии и 0,816 у простого правила; SMAPE 59,4% против 60,8%. Подробности — `docs/experiments.md`.

## Инструкция по сборке

```bash
docker build -t sber-forecast .
```

Образ: `python:3.11-slim` + зависимости из `requirements.txt` (версии зафиксированы), около 1 ГБ.
Модели уже обучены и лежат в `model/`, при сборке и при запросах ничего не обучается; сеть при инференсе не нужна.

## Инструкция по запуску

```bash
docker run --rm -p 8000:8000 sber-forecast
curl http://localhost:8000/health          # {"status":"ok"}
bash tests/test_api.sh                      # самопроверка всех эндпоинтов (нужны curl и jq)
```

Без Docker: `pip install -r requirements.txt && uvicorn app.main:app --port 8000` из корня репозитория.

## Описание API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | `{"status": "ok"}` |
| POST | `/predict` | `multipart/form-data` с файлами `sales` и `stock` (формат обучающих CSV) → CSV-прогноз на 9 недель |
| GET | `/predict?article=…&warehouse=…` | прогноз из последнего POST по артикулу и/или складу (хотя бы один параметр, иначе 400) |
| GET | `/predict/all?format=csv\|json` | весь последний прогноз: 79 101 строка |

- Ответ — CSV `week,warehouse_name,article,quantity`; `quantity` — целые штуки в неделю.
- Первая неделя — понедельник календарной недели, следующей за неделей последней даты в `sales`
  (последняя дата 2026-07-26 → прогноз с 2026-07-27; 2026-07-31 → с 2026-08-03).
- Прогноз строится по всем 11 × 799 парам из `model/config.json`; пары, которых нет во входных данных,
  получают прогноз по пустой истории (как правило, 0).
- Ошибки — `{"detail": "...", "code": "..."}`: 400 — пустой файл, нечитаемый CSV, GET без параметров или неверный
  `format`; 422 — нет обязательных колонок, неверный формат даты (ожидается `YYYY-MM-DD`), история меньше 180 дней,
  отрицательный или нечисловой `quantity`; 409 — GET до первого POST. Отрицательный `stock` допустим (резерв).
- В `stock` колонка артикула по ТЗ — `char_article`; принимается и `article`, как в выданном обучающем файле.
- Время ответа POST на полных данных (≈ 1,5 млн строк продаж, 950 дней) — около 30 секунд.

```bash
curl -X POST http://localhost:8000/predict -F "sales=@sales.csv" -F "stock=@stock.csv" -o forecast.csv
curl "http://localhost:8000/predict?article=char_article_1&warehouse=warehouse_name_3"
curl "http://localhost:8000/predict/all?format=csv" -o full_forecast.csv
```

## Воспроизведение модели и проверка

```bash
# обучение из сырых CSV (по ТЗ — данные только по 2026-07-26 включительно), ≈ 3–5 минут
python -m src.train data/raw/sales_dataset_hakaton_train.csv data/raw/stock_dataset_hakaton_train.csv \
    --cutoff 2026-07-26 --model-dir model --submission submission.csv
# прогноз контейнерным кодом по полным данным совпадает с основным submission
python tests/test_parity.py data/raw/sales_dataset_hakaton_train.csv data/raw/stock_dataset_hakaton_train.csv
```

Обучение и инференс детерминированы (`deterministic=True`, seed 42): `src.train` воспроизводит файлы моделей
и `data/submission_weekly_v6.csv` байт в байт. Проверено и через собранный образ: POST с данными по 2026-07-26
возвращает тот же файл, `tests/test_api.sh` (12 проверок, включая ошибки 400/422) проходит.

## Известные ограничения

- **Качество как у основного submission — при полной истории.** Прошлогодние признаки и сезонная поправка
  требуют не меньше 454 дней данных. С историей 180–453 дня API работает, но эти признаки пустые, поправка равна 1,
  и прогноз грубее (качество в этом режиме отдельно не проверялось). Обучающих данных внутри образа нет, как требует ТЗ.
- Модель обучена прогнозировать 9 недель сразу после последнего дня данных. Если последняя дата не воскресенье,
  прогноз относится к неделям с ближайшего понедельника (разрыв до 6 дней не учитывается).
- Новые склады и артикулы, которых не было при обучении, в прогноз не попадают (сетка — из `config.json`).
- Нулевой прогноз означает «скорее не продастся за эти 9 недель», а не «спроса нет»; сумма прогноза ниже факта
  (в сезонном периоде — около 0,8 фактического объёма), для закупок её нужно поднимать.
- Прогноз кэшируется в памяти процесса: GET-эндпоинты отдают результат последнего POST, после перезапуска
  контейнера нужен новый POST.
